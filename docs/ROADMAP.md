# LIM Roadmap

What's planned for LIM (Landscape Information Manager), what's done, and the rules changes follow.
Tick items off here as they land, and add the release they shipped in.
A Chinese translation is in [ROADMAP.zh-CN.md](ROADMAP.zh-CN.md) (中文版); this English version is the reference.

## Done

Not released yet (branch `dashboard-include-floors`):

- **Dashboard outlook adds up the growth years.** Trees: each growth-year workset's copies as i-Tree calculated them, with the years in between interpolated (trapezoid rule). No more annual × years, which over-reported with worksets. Planting areas don't grow, so they're the Airtable rate × years. Without growth worksets, trees fall back to annual × years, and the outlook line says so.
- **KPI Schedules group the planting schedule by workset** when growth years exist, with a subtotal per year, so a tree isn't counted once per growth year. (Since Phase 3, running KPI Schedules again adds newer columns to existing schedules; delete one only to change its grouping.)
- Dashboard cards include planting-area (Airtable) carbon, runoff, pollution and cost. BNG labels no longer say "primary" twice.

**v1.8.0** (pushed 2026-10-25 on `roadmap-phases-2-5`, not released yet): the web dashboard's 3D can be coloured as the model's Revit views colour trees and floors with their filters (JSON export schema 10, "Colour by"). The BNG tab's floor list scrolls again: a scrollbar at the window's edge (the list's own sat at the far right of the wide table) and the mouse wheel. Every list that selects several rows takes Shift+click for a range — now also Parameters' tick boxes and the web dashboard's result board — and says so above the list.

**v1.7.0** (pushed 2026-10-24 on `roadmap-phases-2-5`, not released yet): the 3D view in the web dashboard — the connector's scene geometry, the family's size formulas in C#, JSON export schema 9 with automatic growth years, and old i-Tree forecasts without sizes requested again. See "3D view in the web dashboard" below. Tested live on the sandbox 2026-10-25.

**v1.6.2** (released 2026-10-23): the BNG tab works scheme by scheme with the Dashboard's schemes (and can make them), and an existing floor's baseline is shared by every existing floor of its type.

**v1.6.1** (released 2026-10-23): a fix: the Dashboard's saved schemes (Scheme A, Scheme B, …) are offered again when it's reopened.

**v1.6.0** (released 2026-10-23, the first release since v1.4.0, so it carries v1.5.0 too): everything below down to v1.4.0, including Refresh and Audit and Health Check removed in favour of the Dashboard's Model checks, Save shared parameter file, Floor Calculator and Connectivity in steps, Site details, the connectivity heatmap view and the web dashboard's growth curve.

From now on every update pushed to GitHub gets the next minor version.

## 3D view in the web dashboard (in progress, 2026-10-24)

The web dashboard shows the site in 3D: the trees and planting areas of the chosen scenario and growth year, matching its figures. Researched first (Speckle, Autodesk Data Exchange and APS Viewer, Sketchfab, Cesium, iTwin, Twinmotion and others): LIM exports a compact scene and the page draws it with three.js, free and with no viewer accounts.

- **Scope (your call):** trees and floors only; floors as their top face, holes shown; proposed scenarios leave demolished elements out; the existing site as the Dashboard has it (primary options, first phase); automatic growth in the first version; the 3D view always matches the scenario's figures.
- [x] **Phase 0 on the sandbox (by script, read-only):** all 930 trees match the planting family's formulas within 1 cm; 21 floors with up to 59 holes, each triangulated top face within 0.3% of Revit's area.
- [x] **Old i-Tree forecasts are requested again:** forecasts stored before 2026-10-23 carry no height or crown, and Tree Calculator never recalculated a stored forecast. A forecast without sizes now counts as missing (`TreeTimelines.HasSizes`).
- [x] **Connector `get-scene-geometry`** (`SceneGeometryService`): every tree's trunk base, drawn size and what it grows from (age at planting, projected year, stored i-Tree size); each planting type's growth rates, maximum size and `Mature Age`; every floor's top face triangulated with its holes cut out. All design options and phases. Connector change: needs the next install.
- [x] **`TreeSizeForecast`:** the family's size formulas in C# (trunk H/3, crown 2H/3, radius W/2; i-Tree's size when there is one, not capped at the maximum, as in the family; else the type's rates over its growth years, capped).
- [x] **JSON export schema 9:** a `scene` (trees, floors, growth profiles) and, on every entry, `sceneTrees` / `sceneFloors`: exactly the elements its figures come from. Without Growth Projections copies, a model that can grow its trees gets growth years 0/5/10/15/20/25 (and the design year), every tree grown by the family's formulas and the canopy figures from the same sizes. Written compact. Checked with the export code on the sandbox's data: 930 trees, 56 floors, 1.3 MB; Scheme A's canopy 12 → 7,223 m² from year 0 to 25.
- [x] **Web dashboard (LandscapeCoBenefitsDashboard, on GitHub Pages since 2026-10-25):** a "3D site" panel following the scenario and growth year (three.js from jsDelivr, fetched only for a file with a scene), and a result board in the table language — trees by species, planting areas by landscape type — whose selected rows filter the 3D view; clicking a tree or area shows its card and flashes its row. A species keeps one colour in every scenario and year (ranked once per file), in the charts, the board and the 3D. Older exports load as before. Checked in headless Edge on the export above: no script errors.
- [x] **Tested live (2026-10-25):** the installed connector gives 930 trees, 51 floors (23 with holes); Tree Calculator refreshed the old forecasts; the web dashboard's sample is a live export of the sandbox.
- [x] **Colour by Revit's view filters (v1.8.0, schema 10, your call: Revit's current values, every view, floor "Use" colours too):** the connector reads every view whose enabled, visible filters colour trees or floors (`SceneColourSchemeReader`), and Revit itself tests each element against them (`PassesFilter`, first filter in the view's order wins), so the 3D colours exactly as the view, whatever the rules. Legend labels come from the rules: bands of one number ("4–8", "≥ 24", in the project's display unit, "/yr" for an annual figure, or the unit the filter names end with for a plain number), a text a filter equals, else the filter's name. Views that colour the same way count once, under the shortest name on a sheet ("O2", not "Habitat O2"). The web page's **Colour by** list, a legend with counts that filters the 3D (Shift+click for a range), and each element's value on its card. On the sandbox: 12 schemes in 0.2 s, among them O2, CO2, Avoided water, Pollution, the four planting-area rates and the connectivity heatmap. The 3D Aerial View's floor "Use" filters colour nothing yet — every floor's `*Use` is empty — so they appear once floors have a Use. Connector change: needs the next install (Revit closed); the sample was made by running the new reader through pyRevit.

## Tree growth in the family (in progress)

The planting family computes the tree's age; LIM supplies the inputs.

- [x] `!_S_PLT_TreeGrowth_ProjectedYears_Number` (Instance): Growth Projections writes the growth year (0 = Baseline, 5, 10, … from the workset).
- [x] **The projected year decides the workset (2026-10-22, your call):** a tree's `ProjectedYears` says which growth-year workset it belongs on. The automatic age update only fills an empty `ProjectedYears` from the workset and no longer overwrites one you set; a tree whose year differs is counted ("Sort & check trees moves them"). Create & refresh treats a hand-placed tree with a projected year above 0 as a growth-year tree, not an original to copy or move back to Baseline.
- [x] **Copies are labelled and pinned (2026-10-22):** Growth Projections writes `!_S_PLT_TreeGrowth_GeneratedBy_Text` (new, Instance, Identity Data) on every copy it makes or refreshes, e.g. "LIM Growth Projections: 10-year copy of tree 666206. Edit the original tree, not this copy.", and pins it. It unpins a copy while refreshing or deleting it. Needs Import Shared Parameter; the sandbox's 63 copies get it on the next run.
- [x] **Year 0 is the project start (2026-10-22):** the year-0 workset is "LIM_Growth_0yr - Project start", not "- Baseline": Baseline means the Existing phase (BNG). Old names still read as year 0.
- [x] **New trees are drawn grown, at the design year (2026-10-22, your call):** every tree that isn't a Growth Projections copy is an original, drawn at its own year: its `ProjectedYears` when above 0, else by phase, existing trees as they stand today (year 0) and new ones at the design year (Growth Projections > "New trees drawn at", default 25, saved on the project). Copies are made only for the years you list, never for an original's own year (a leftover one is removed), so new trees get no year-0 copy. Sort & check trees and Create & refresh put each original on its year's workset and write its year. i-Tree's forecast for a new tree drawn grown starts at the planting DBH (5.4 cm), for an existing tree at today's DBH, so the yearly benefits don't depend on the year a tree is drawn at. Trees now carry whether they are new and whether they are copies; the Dashboard's forecast counts originals, not year-0 trees.
- [x] **Modelling convention (agreed 2026-10-22):** the main model holds the existing site (first phase); design options hold the schemes. Existing retained: created Existing, not demolished. Existing lost: created Existing, demolished New Construction (split the existing floor so the demolished part sits exactly under the new work). Enhanced: retained plus `!_S_PLT_BNGInput_Enhanced_YesNo`. New: created New Construction. Floors never overlap within a phase. Revit can't demolish a main-model element in one option only, so existing parts that schemes treat differently go into every option of that set. Existing trees: AgeAtPlanting = their age today, year 0.
- [x] **Dashboard counts phases (2026-10-22, schema 7):** a scheme's benefits, areas and maintenance count only what stands after development (demolished trees and planting areas are left out); BNG still takes the lost floors for its baseline. A new "Existing site" scenario (what stood in the first phase) is the default reference in the scenario overview, so every scheme compares against the existing site; its BNG is the baseline, no change. The JSON export marks it `isExistingSite`. Trees carry their phase role from the connector (floors already did through BNG).
- [x] **Sandbox remodel (2026-10-22, by script, not synced, one undo step each):**
  - 2,139 trees moved from Workset1 onto the year-0 workset.
  - 41 duplicate floors deleted (copies pasted 2-3 times in Test : Option 1 and Variante 1 : Baseline), and one stale meadow in Test : Option 1 (78,248 m²) lying over the current one and the shrub.
  - Main model = existing site only: its 10 new floors, 540 new trees and their 42 growth copies deleted; the options' copies of the 5 existing floors deleted.
  - The scheme split by geography at x = 187.8 m (equal areas): Variante 1 keeps the west, Test the east. "Variante 1 : Baseline" renamed "Option A". Deliberate differences: Variante 1 Option A = surfaces + 239 trees, Option 1 = trees only, Option 2 = 80 trees; Test Option 1 = surfaces + 301 trees, Option 2 = meadow and shrub as lawn, half the trees (its hand-made 25-year trees became year 0); the Empty options stay empty.

- [x] **Sandbox clean-up (2026-10-22, by script, not synced):** deleted 546 overlapping duplicate trees (same workset, design option and type, within 0.1 m), 542 of them in "Variante 1 : Baseline", which had been pasted twice; one undo step. 3,490 trees became 2,944, each design option 540 (Variante 1 : Option 2: 181). "Test : Option 2" is a hand-made 25-year layout on LIM_Growth_25yr (540 trees): still to decide whether to keep it.
- [ ] **Growth Projections > Sort & check trees (built 2026-10-22, not run on the sandbox yet):**
  - **Sort into worksets:** moves every tree onto its projected year's workset (a Growth Projections copy onto its link's year), creating missing worksets; one undo step. Grouped trees and years outside 0–100 are listed instead.
  - **Overlapping trees:** trees within a set distance (0.1 m by default) of another on the same workset in the same design option, of the same type unless unticked. One per place is kept (the original its copies project, else a tool-made copy, else the oldest); the rest turn red in the active view, with Select, Reset colours and "Delete the red trees" (one undo step, with the growth-year copies made from them).
- [x] `!_S_PLT_TreeGrowth_AgeAtPlanting_Number` changed from Type to **Instance**, same GUID. Import Shared Parameter moves each type's value onto its trees, and growth copies inherit their original's value.
- [x] Fallback: while a family has no formula yet (its `Years` is still editable), LIM keeps setting `Years` itself, capped as before.
- [x] `WWP_Vegetation_Tree` family (2026-10-21, saved by you):
  - `Mature Age` (family type parameter) = `roundup(MaxHeight / (HeightRatio × 1000 mm))`, worked out from the family's own data. 0 means no max height.
  - `Years` = `AgeAtPlanting + ProjectedYears`, stopped at `Mature Age`. With no max height it's `AgeAtPlanting + min(ProjectedYears, 25)`.
  - `DBH` = `5.4 cm + (Years − AgeAtPlanting) × TrunkDiameterbyYear × 1 cm`, so it grows from the 16/18-girth planting size and stops at maturity.
  - Height and width caps now compare real metres. 16 types had their max size typed in mm; those were converted.
- [ ] **Growth rates from i-Tree:** the family grows DBH by `!_S_PLT_GrowthRatio_TrunkDiameterbyYear_Number` (cm/yr), and height and crown width by `..._HeightbyYear_Number` / `..._WidthbyYear_Number` (m/yr) until i-Tree gives the tree its own size (below).
  - [x] **Trunk (built 2026-10-21):** i-Tree's forecast reports DBH for every year, and grows a trunk by the same amount each year for one species, condition and crown exposure (Acer campestre: 0.44 cm/yr at Good, exposure 3; 0.78 at exposure 5), so its slope is the family's rate exactly. Every planting type with a species code is rated at the condition and exposure most of its planted trees have (Good, 3 when it has none): one forecast per species, condition and exposure.
  - [x] **Height and crown width (2026-10-22, your call: i-Tree replaces the sheet's values):** i-Tree's forecast also reports height and crown area for every year. They start from a planting size and slow down (Quercus robur, Good, 3: 6.34 m tall at planting, +0.41 m in year 1, +0.30 m in year 25), so no rate from zero fits every year: the rate is i-Tree's size at the design year divided by the design year (Quercus robur: 15.21 m and 8.04 m after 25 years, so 0.61 and 0.32 m/yr). A tree drawn at the design year is then i-Tree's size even before it's calculated. The height rate also sets `Mature Age`.
  - [x] Growth Projections step 3 is now **Growth rates** (trunk, height, width). **Write to types** sets all three on each Revit type (preview, one undo step). **Push to sheet** replaces them in the Airtable sheet's "Trunk diameter annual growth rate (cm/yr)", "Height year annual growth rate (m/yr)" and "Width annual growth rate (m/yr)" columns, adding any that are missing; the Importer maps all three onto the types.
  - [x] **What's already there (2026-10-22, your call):** each type shows whether its Revit type and its Airtable row already have the i-Tree rates: Up to date (skipped), Stale, Missing or No row, with what would change on hover. Write and Push only change what differs and say how many were skipped.
  - [x] Ran on the sandbox (2026-10-22): Write to types wrote 18 rates on 9 types (the 9 trunk rates were already there).
- [x] **Copies wait for their design option (2026-10-22):** Revit adds new elements only to the active design option, and the API can't change which one is active. With every sandbox tree in an option and the main model active, Create & calculate made each copy, found it in the wrong option, deleted it, and still showed the step done, so only year 25 existed. The preview now counts the copies waiting for each option, the run skips them, and the step stays open naming the options to make active in turn (status bar > Design Options). Connector change, installed 2026-10-22 19:55.
- [x] **By design option (2026-10-22, your call):** Create & calculate has a table of every design option: its originals, the copies made of the ones they need (an original needs one per growth year except its own), the missing years, the trees i-Tree still has to calculate, and what to do: Done, Run, or make the option active first. Works with the installed connector.
- [x] **Four steps, batches (2026-10-22, your call):** the Results step is gone: Create & calculate's table now also counts the trees that need inputs, and the scan's notes (ages updated, wrong workset, DBH that doesn't grow) sit under it; the step is done when every option has its copies and every tree is calculated. The step shows the trees in scope (from step 1). Copies are made 500 at a time (each batch its own undo step, the existing copies refreshed once) and i-Tree calculated 500 trees at a time. Revit still adds copies only to the active design option, so the other options wait for their turn. Batching is a connector change: until the next install a run makes its copies in one go.
- [x] **The design year is the base (2026-10-22, your call):** the Dashboard opens on the design year (25, from the project) instead of 10, and the JSON export marks the default scenario's design year as primary, so the web dashboard opens there too. Growth Projections' tables mark the design year and put the originals on the workset they're on (not year 0). Sandbox: the six tree schedules count originals only (`!_S_PLT_TreeGrowth_GeneratedBy_Text` has no value), and the 5- and 10-year views on XX-0003 show their own year's workset.
- [x] **Trees drawn at i-Tree's size (2026-10-22, your call):** i-Tree estimates a tree's height and crown from its DBH (LIM sends it no height or crown), so the drawn tree now uses i-Tree's numbers. Two new Instance parameters (Analysis Results): `!_S_PLT_iTreeResult_TreeHeight_Length` and `!_S_PLT_iTreeResult_CrownWidth_Length` (the width of a circle of i-Tree's crown area). Every i-Tree calculation (Tree Calculator, Growth Projections, Refresh and Audit) writes them for the tree's DBH, and 0 when i-Tree can't calculate it. The family draws trunk height = height / 3, foliage height = 2 × height / 3 and crown radius = width / 2 from them, and from the growth rates while they're 0. DBH stays the family formula: it's i-Tree's input, and with i-Tree's trunk rate it equals i-Tree's DBH every year. A tree whose age a tool changes (Growth Projections, the automatic age update) loses its i-Tree size until it's calculated again, so a copy never keeps its original's size. Import Shared Parameter adds them to the project for schedules.
- [x] **Family geometry (2026-10-22, loaded into the sandbox; the family file isn't saved):**
  - `TreeOverall_Height = TreeFoliage_Height + TreeTrunk_Height` (it added the trunk diameter).
  - `TreeTrunk_Diameter = TreeTrunk_DBH_Diameter`: the drawn trunk follows DBH (it was 7.5 cm on every tree).
  - `TreeRoot_Diameter` is at least 4 × the trunk diameter, so the root profile can't fold over on a tiny tree.
  - `Mature Age` and the height and width caps treat a max size under 1 m as missing.
  - Tested before loading: every type at 8 ages (0 to 40 years, with and without i-Tree sizes), no failures. All 1,010 sandbox trees kept, each with trunk, crown and roots.
- [x] **Max sizes stored as mm (fixed 2026-10-22):** 16 sandbox types had their max height and width in mm (Prunus_Avium 20 mm × 12 mm), so `Mature Age` was 1 and their 75 trees were stuck at year 1, 20 mm tall. Set from the Airtable sheet, which is in metres (Prunus_Avium 20 m × 12 m, Mature Age 34). Health Check now warns about tree types with a max size under 1 m.

## Phase 2: Design-option scenarios

Every dashboard number depends on picking the right scenario, so this comes before the redesign. Built on branch `roadmap-phases-2-5`, not released yet.

- [x] **Scenario picker:** one option per design-option set, defaulting to each set's primary. A scenario is the main model + the chosen option in every set; elements in options that aren't chosen are left out. The connector lists every set and option, including empty ones (`DesignOptionSetItem`).
- [x] **"Use current view":** works out the scenario from the options visible in the active view (a view collector per option; a set with nothing visible falls back to its primary). Also in Edit… as "Fill from Revit's active view".
- [x] **Canopy cover per scenario:** the union of canopy footprints, overlaps counted once (exact, `CanopyUnion`), ÷ the chosen site area. Trees now carry their plan position; a cached snapshot without positions falls back to summed areas.
- [x] **Greenspace ratio:** pervious ÷ (pervious + impervious) floor area, on Site & Biodiversity and in the scenario overview. Unclassified floors and building slabs (structural floors, "slab"/"suspended"/… types without an LDS type, or tagged `Building`) are listed separately and left out.
- [x] **A "design option" means a scenario:** saved scenarios are named and stored on the project (`ProjectSettingsSnapshot.DesignScenarios`), shown as e.g. "Scheme A = Variante 1: Baseline + Test: Option 1". The Dashboard, BNG tab (as a filter) and JSON export (schema v5, `designOption` + `choices`) all work on the scenario.
- [x] **Scenario overview:** one table with every saved scenario next to the others, plus the difference from a chosen reference scenario (absolute and %; percentage metrics in points). The reference is saved on the project.
- [x] **Performance comparison:** for each scenario, trees, species, canopy cover, greenspace ratio, CO₂e, runoff avoided, pollution removed, oxygen, BNG units/net gain, embodied carbon, ecosystem value, maintenance cost and net value, side by side and as bar charts (lower is better for embodied carbon and maintenance).

## Rules for changes

### Parameter names

- **Calculated values:** start with `!_S_PLT_Result_…`. Exceptions kept for existing projects: `!_S_PLT_iTreeResult_*`, `!_S_PLT_BNGResult_*` and `!_S_PLT_ConnectivityResult_*`.
- **Sheet reference rates:** per tree or per m², on the Type, named `…Rate_Number`, never `_Mass`/`_Volume`.
- **Sheet formula columns:** get no parameter; LIM calculates them.

### Renaming or retyping a parameter

- Give it a **new GUID**, add the old name to `legacyAliases` in `SharedParameterSetupService`, and remove the old row from `Shared_Parameters_WWP.txt`.
- **Never** reuse a GUID under a new name, and never give an existing name a new GUID. Projects identify parameters by GUID, so either one breaks them.
- If a name returns to an earlier one, reuse the GUID it originally shipped with.
- Safety net: `ResultParameterReusePolicy` lets Import Shared Parameter keep an existing BNG/Connectivity *result* parameter whose name and type match but whose GUID differs. It's for projects bound from older catalogs, not a substitute for the rules above.

### Shared parameter file

- `Shared_Parameters_WWP.txt` is UTF-16 LE with BOM and CRLF line endings. Edit it with a script, never by hand in an editor.
- It's embedded into the connector at build time, so update it before running `Package-Addin.ps1`.
